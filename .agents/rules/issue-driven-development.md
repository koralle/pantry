# Issue Driven Developmentルール

GitHub Issueを、機能要件およびプロダクト要件の正本として扱う。

このルールは、GitHub Issueを起点として作業する場合に従うべき開発プロセスを定義する。

## 実装開始条件

原則として `spec:ready` ラベルが付いているIssueだけを実装対象とする。

`spec:draft` のIssue、または実装を妨げる「未解決事項」が残っているIssueを実装してはならない。

ラベルとIssue本文の状態が矛盾している場合は、実装を開始せず、その矛盾を報告する。

## 仕様の正本

現在のIssue本文を、そのIssueに関する唯一の仕様の正本として扱う。

Issueコメントには、議論、質問、過去の経緯、調査結果、実装計画などの補助情報を記録してよい。ただし、コメントはIssue本文を上書きする仕様として扱ってはならない。

コメント上の決定によって仕様が変更された場合は、実装を進める前にIssue本文へ反映されていることを確認する。

Issue本文とコメントが矛盾する場合は、Issue本文を優先する。

コメントにしか存在しない内容を要件として推測してはならない。

## Issueと実装の責務

Issueには「何を実現するか」と「なぜ実現するか」を記述する。

実装計画およびPull Requestには「どのように実現するか」を記述する。

Issueに書かれた実装案は、明示的な制約として定義されていない限り、必須の実装方法として扱わない。

## 計画前

実装計画を作成する前に、以下を実施する。

1. 現在のIssue本文を最後まで読む
2. 補助情報として関連するIssueコメントを読む
3. リポジトリ内の適用対象ルールを読む
4. 既存のリポジトリを調査する
5. Issueに関係する既存のアーキテクチャ、抽象化、慣習、テストを把握する
6. 曖昧さ、矛盾、不足している要件、既存実装との衝突を確認する

この段階では、本番コードを変更しない。

Issueに実装を妨げる未解決事項、矛盾、または振る舞いに影響する曖昧さが存在する場合は、解釈を独断で決定してはならない。

問題点を報告し、仕様が確定するまで実装を開始しない。

## 実装計画

Issueとリポジトリの双方を調査した後に実装計画を作成する。

実装計画は、以下を根拠として「どのように実現するか」を決定する。

- 現在のIssue本文
- 既存のリポジトリアーキテクチャ
- 既存の抽象化および慣習
- 適用されるプロジェクトルール

実装計画には最低限、以下を含める。

- 採用する実装方針
- 主に影響を受ける領域
- 再利用する既存の抽象化
- 重要な技術的判断
- 必要なテストおよび検証方法
- 既知のリスクやトレードオフ

実装開始前に、実装計画を対象Issueのコメントとして記録する。

実装計画は仕様ではなく、Issue本文を上書きしない。

## 実装開始前

コードを変更する直前に、現在のIssue本文を再度確認する。

実装計画作成後にIssue本文が実質的に変更されている場合は、コードを変更する前に計画を見直す。

`spec:ready` が解除されている場合は実装を開始しない。

古い実装計画やコメントにしか存在しない要件を実装してはならない。

## 実装

Issueで要求されている振る舞いを、既存のリポジトリアーキテクチャと慣習を尊重して実装する。

正当な理由がない限り、新しい並行した抽象化を導入するより、既存の抽象化を拡張・再利用することを優先する。

パフォーマンス劣化を伴う設計は、明確な利益と根拠なしに採用しない。

以下を暗黙的に行ってはならない。

- 要求されている振る舞いを変更する
- スコープを狭める
- スコープを広げる
- 受け入れ条件を無視する
- プロダクト上の曖昧さを独断で解決する
- Issue本文と矛盾する振る舞いを追加する
- 技術的に簡単という理由だけで仕様を変更する

実装中に、要件が実現不可能、安全でない、矛盾している、またはIssueから想定される範囲を大幅に超えて複雑であることが判明した場合は、独断で仕様を変更せず問題を報告する。

技術的な困難は、仕様を再解釈する権限を意味しない。

## Issue本文の変更

仕様の更新を明示的に指示されていない限り、実装エージェントはIssue本文を編集しない。

受け入れ条件のチェックボックスを、実装進捗の管理目的で変更してはならない。

実装状況はIssue本文ではなく、実装プロセスおよびPull Request上で管理する。

Issueコメントには以下を記録してよい。

- 実装計画
- ブロッカー
- 質問
- 調査結果
- 関連Pull Requestへのリンク

コメントを、仕様本文を更新する代替手段として使用してはならない。

## 検証

実装完了後に、現在のIssue本文を再度最後まで読む。

以下のすべてに対して実装を検証する。

1. すべての要件
2. すべての該当する受け入れ条件
3. すべての制約
4. 記載されているすべてのエッジケース
5. バグ修正の場合は、回帰させてはいけない振る舞い

リポジトリで要求されている自動検証を実行する。

該当するものには以下を含む。

- テスト
- 型チェック
- Lint
- フォーマットチェック
- ビルド
- その他プロジェクト固有の検証

満たしていないことが分かっている受け入れ条件が存在する状態で、Issueを完了扱いしてはならない。

## Pull Request

Pull Requestから対象Issueを参照する。

Pull RequestのマージによってIssueを完全に解決する場合は、GitHubのClosing Keywordを使用する。

例:

`Closes #123`

Pull RequestにはIssue本文を繰り返すのではなく、実際にどのように実装したかを記述する。

Pull Requestの「受け入れ条件の検証」には、関連Issueの最新版にある受け入れ条件を基準として結果と証跡を記録する。

Issue本文からの差異がある場合は、Pull Request上で必ず明示する。

実装詳細の中に仕様との差異を隠してはならない。

意図的にIssue本文と異なる実装を採用する場合は、先にIssue本文を更新して仕様レビューをやり直すか、差異が解消されるまでPull Requestを完了扱いしない。

## 最終整合性確認

作業を完了扱いする直前に、以下を実施する。

1. 現在のIssue本文を再度読む
2. Issue本文と最終実装を比較する
3. Issue本文とPull Requestの説明を比較する
4. すべての受け入れ条件を検証する
5. 実装上の判断によって仕様が暗黙的に変更されていないことを確認する
6. 不要なスコープ拡大が含まれていないことを確認する

Issueと実装が表現する観測可能な振る舞いは一致していなければならない。
